Never point development or test configuration at the production database. Use the templates in deployment/environments; actual .env files remain private to each machine.

Standard feature flow

Feature request → scope/acceptance criteria → feature branch → development tests
→ pull-request review → staging deployment + user acceptance → tagged release
→ production backup + deployment → smoke test → monitoring → release record
  • Write the business need, users affected, data fields, success criteria, security/privacy impact, and rollback plan.
  • Create a branch such as feature/tracker-escalation from the protected main branch.
  • Implement code, tests, documentation, and a new numbered migration if schema changes are required.
  • Run python scripts/verify_release.py and pytest locally.
  • Open a pull request. CI must pass before merge.
  • Deploy the approved commit to the isolated test/staging server. Apply migrations against the test database only.
  • Manager/operator tester completes acceptance cases, including permission checks and Power BI impact.
  • Update CHANGELOG.md; create an annotated Git tag such as v1.2.0.
  • During a scheduled production window, take a verified database backup, deploy exactly that tag, apply new migrations once, and run the production smoke test.
  • Record the release owner, time, backup reference, migration list, test result, and outcome.

Database migration rules

  • Migrations are forward-only and sequential: 006_description.sql, then 007_description.sql.
  • Never edit a migration that ran in any shared/test/production environment.
  • Test every migration on a restored copy of production-like data before production.
  • Create backward-compatible changes first: add new columns/tables, deploy code, migrate data, then retire old fields in a later release.
  • A code rollback does not automatically undo a database migration. For a risky migration, create and test a specific recovery migration or restore plan.

Production deployment checklist

  • [ ] Approved Git tag and changelog entry.
  • [ ] CI, pytest, and python scripts/verify_release.py passed.
  • [ ] Staging user acceptance completed.
  • [ ] Privacy/security impact reviewed.
  • [ ] Verified database backup and restore point recorded.
  • [ ] Maintenance window communicated.
  • [ ] New migration list reviewed; migration administrator account available temporarily.
  • [ ] Deploy exact tagged source to the factory server.
  • [ ] Install locked dependency versions and restart services.
  • [ ] Run migrations once, then restore restricted application credentials.
  • [ ] Smoke test operator entry, manager PIN, tracker permissions, and Power BI read-only access.
  • [ ] Monitor errors and record release completion.

Rollback decision

If the smoke test fails, stop further use, return the application code to the last known-good tag, and use the pre-deployment backup/recovery plan if data integrity is at risk. Do not delete production data to make a rollback appear successful. Escalate to IT/management for any database restoration.
