Test/staging environment setup

Purpose

Staging is a separate, non-production copy of the system used to validate updates before they reach operators. It is the required safety gate for database migrations, UI changes, manager permissions, Power BI changes, and future AI work.

Minimum setup

  • A separate Windows computer or isolated virtual machine, not the factory production server.
  • Separate MySQL instance/database: slurry_management_test plus system_import created by migrations.
  • Separate restricted MySQL account: slurry_test_app@localhost.
  • Separate test hostname, TLS certificate, .env, manager PIN, and Power BI test workspace.
  • Sanitized representative records only. Do not copy personal/free-text sensitive production data without approval.

Copy deployment/environments/.env.test.example to the test server as .env, replace every placeholder locally, install dependencies, and apply migrations with the temporary test migration administrator.

Acceptance test baseline

Before every release, confirm:

  • Production record saves and appears in history.
  • Invalid qualified quantity is rejected.
  • Abnormality report saves and open tracker updates work.
  • Operator cannot open analysis/dashboard endpoints.
  • Manager PIN unlocks dashboard, analysis, and field configuration; sign-out ends access.
  • Power BI test user can read reporting tables but cannot change them.
  • New/changed fields appear correctly and are stored in MySQL.
  • Migration runs once and is safe when the application restarts.
  • Regression tests, release verification, and a basic performance check pass.

Promotion rule

Only the exact commit tested in staging may be tagged and promoted to production. If code changes after acceptance, repeat the staging cycle.
