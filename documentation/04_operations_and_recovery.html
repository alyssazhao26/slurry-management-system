Operations, backup, and recovery

Daily operating checks

  • [ ] Factory server is powered on and reachable through the internal HTTPS link.
  • [ ] MySQL service, web app service, and HTTPS proxy service are running.
  • [ ] Employees use https://slurry-management.local; a certificate warning is an issue to resolve, not something to bypass.
  • [ ] Disk space is sufficient for MySQL and backups.
  • [ ] The latest manual backup completed successfully.
  • [ ] A sample operator entry can be saved and viewed in its record table.

Backups

The included script creates a consistent MySQL .sql backup. To keep that backup encrypted at rest, set its destination to a separate BitLocker-encrypted data drive or an IT-managed encrypted backup location. Do not store backups in the MySQL live-data folder or the project folder.

Example concept (adapt credentials and backup path; do not place passwords in a script):

mysqldump --single-transaction --databases slurry_management system_import > D:\ApprovedBackups\slurry_YYYY-MM-DD.sql

The backup task must run under a restricted account and write only to the approved backup location. Verify completion, file size, and restore capability—not merely that a file exists.

Current backup process: manager-initiated manual backup

In the manager workspace, unlock the page with the manager PIN and select Create manual backup / 创建手动备份. The server runs scripts\backup_factory_database.ps1, creates a consistent MySQL .sql backup using --single-transaction, and stores it in BACKUP_DIRECTORY (default C:\GNEM_Backups). The backup is never downloaded to the browser and database credentials are never shown in the page.

For this pilot, if the optional DB_BACKUP_USER and DB_BACKUP_PASSWORD are blank, the backup script uses the private application database credentials in .env. When the system is formally deployed, replace that fallback with a separate backup-only MySQL account and an encrypted/off-server backup destination.

The project keeps scripts\install_maintenance_tasks.ps1 as an optional future scheduler. Do not run it for the current manual-backup process. If automatic backups are introduced later, configure a separate backup account, protected destination, retention period, and restore test first.

Restore test

At least quarterly, restore a recent backup to a separate test MySQL instance:

  • Confirm the backup file can be read.
  • Restore slurry_management and system_import to a non-production test server.
  • Confirm production and abnormality record counts are plausible.
  • Confirm recent records and field definitions are present.
  • Record the date, operator, backup tested, and result.

Never experiment with a restore on the live production database.

Incident response

SituationImmediate action
Server unavailableTell operators entries are not being saved; use approved paper contingency records; contact IT
Suspected unauthorized accessDisconnect the server from the network if directed by IT; preserve logs; rotate passwords; investigate before reconnecting
Incorrect recordUse the approved tracker/update process and document the correction; do not directly edit MySQL tables without authorization
Database corruption/hardware failureStop the application, preserve evidence, restore to replacement hardware from the latest verified backup, validate before reopening entry

Application updates

  • Back up the database and project folder.
  • Test new code on a non-production copy when possible.
  • Put the server into a short maintenance window.
  • Copy the approved code update.
  • Back up before applying any new migration.
  • Run migrations once with the temporary migration administrator account.
  • Restore the restricted web-app account, restart services, and run the acceptance checks.

Never edit an already applied migration. Add a new numbered migration instead.

HTTPS recovery check

If employees cannot connect, run Start_GNEM_Slurry_Tracker.cmd on the factory server. If the script reports a Caddy error, inspect logs\caddy.stderr.log. Confirm that port 443 is listening, the server is awake, and the device has the required hosts/DNS entry and trusted factory root certificate. Do not work around the issue by returning users to port 5000.
