Future AI integration guide / 未来 AI 集成指南

This guide is provider-neutral. You may write your own LLM integration later; do not put API keys, prompts, or model calls in the employee browser.

Approved source data

Table Useful data Use for AI
system_import.production_records Date, shift, J1–J8 machine, formula, batch, planned/actual/qualified quantities, pending-qualified flag, achievement rate, qualified rate, notes, timestamps. Production summary, variance explanation, low yield/quality patterns, missing-qualified follow-up.
system_import.abnormality_reports Date, time range, machine, Semi/Auto type, event type, severity, description, immediate action, calculated duration, resolved state, time-cost flag, cost-failure JSON list, responsible person, target/actual finish, solution, timestamps. Cost-failure classification suggestions, event summaries, repeated-issue patterns, overdue-event review.
system_import.cost_failure_types Active type code, bilingual display name, definition. Allowed labels for structured cost-failure classification.
system_import.event_type_options Active event-type choices and display order. Valid event taxonomy for classification and trend analysis.
system_import.field_definitions Manager-configured optional form fields and choices. Interpret custom fields only when approved for AI use.

Do not send slurry_management.audit_events, manager sessions, passwords, PINs, API keys, or unnecessary personal information to an external model.

Recommended account and permission boundary

Create a separate slurry_ai MySQL account, restricted to the manager/AI computer IP. Grant it SELECT only on system_import.*. It must not update employee records, access slurry_management, or use a wildcard host such as '%'. Use a separate AI account even if Power BI already has read-only access, so its password can be rotated without breaking reporting.

CREATE USER 'slurry_ai'@'MANAGER_AI_COMPUTER_IP' IDENTIFIED BY 'LONG_RANDOM_PASSWORD';
GRANT SELECT ON system_import.* TO 'slurry_ai'@'MANAGER_AI_COMPUTER_IP';
FLUSH PRIVILEGES;

Safe data flow

Manager-only screen → your server-side AI service → read-only slurry_ai query of system_import → curated/redacted record JSON → chosen model API over HTTPS → structured manager review result

The employee browser must never call the model API directly. Store the model API key only in the manager/AI service environment variables, for example LLM_API_KEY; keep it out of GitHub, browser JavaScript, and SQL tables.

Best first AI use cases

  1. Cost-failure suggestion: send an event's description, event type, severity, machine type, duration, and the active definitions from cost_failure_types. Require JSON containing only allowed type codes, a confidence level, and a short bilingual explanation. Show it as a manager suggestion; do not automatically change the employee record.
  2. Manager daily summary: combine selected-day production totals and event data into production variance, qualified-pending items, open/overdue events, repeated event types, and questions for follow-up.
  3. Recurring-issue review: use SQL first to group by machine, formula, event type, severity, and date range. Give aggregates to the LLM to explain patterns. This is cheaper and safer than sending every historical raw record.
  4. Data-quality check: flag missing times, missing qualified quantities, invalid-looking descriptions, and unresolved events past target finish. Rule-based checks remain source of truth; the LLM explains rather than decides.

What AI cannot reliably do yet

Because data is manually entered and no machine sensor/PLC data is connected, the model cannot diagnose machine condition or predict failure with engineering reliability. It can identify record patterns and suggest questions, not prove root cause or make safety, maintenance, or production decisions.

Result storage and audit trail

When you later implement your service, create a manager-only analysis table in slurry_management, not in reporting tables. Store analysis ID, source record IDs/date range, model/provider name, model version, prompt version, run time, status, structured JSON result, reviewer, reviewer decision, and a hash of supplied input. Avoid storing API keys and unnecessary raw prompts. Never let an AI response directly close an event, overwrite a cost-failure type, or modify a production record.

Before enabling any external API

  • Confirm which data can leave the factory network and review the provider retention/training settings.
  • Use HTTPS, server-side timeouts, rate limits, retries with idempotency, and a per-run cost limit.
  • Validate every model response against an allow-list/schema before displaying or storing it.
  • Keep a manager approval step and audit record for every result.
  • Start with a small historical test set and evaluate accuracy against manager-labelled examples before showing suggestions.
