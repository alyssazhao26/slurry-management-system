GNEM Slurry Production Tracker System documentation

Final production cutover / 最终生产部署

Use this checklist when moving the tested project to the final always-on factory server. It preserves the working structure, keeps passwords out of GitHub, and avoids deleting records.

1. Keep both MySQL schemas

Schema Purpose Who uses it
slurry_management Protected application tables: audit history, manager functions, exception queue, migration history. GNEM web app only
system_import Clean operational/reporting tables: production records, event tracker, field definitions, sync receipts. GNEM web app and read-only Power BI

Both are necessary in the current code. This is a useful industry-standard separation: the operational app area is protected, while reporting connects only to the controlled import schema. Do not delete either schema.

2. Keep the migration history

The migration runner currently executes two files in order: 001_initial_schema.sql creates the baseline, and 002_approved_feature_round.sql applies every approved database change from this development round in dependency order. Earlier pre-baseline history remains under migrations\legacy_prebaseline for audit only and is not executed. After deployment, never edit a migration already applied to that department database; add the next unique numbered migration instead.

3. Create the three MySQL accounts

Open MySQL Workbench on the final server as the MySQL administrator. Copy deployment\sql\create_production_accounts.sql.template to a private temporary file, replace every password placeholder with a long random password, replace POWERBI_GATEWAY_IP with the approved Power BI computer/gateway IP, then run it. Never save the completed version in GitHub or a shared folder.

Account Used for Permissions
slurry_web_app@localhost GNEM employee and manager web application Read, add, and update only; it cannot change database structure.
slurry_powerbi@POWERBI_GATEWAY_IP Power BI import/refresh Read-only access to system_import only.
slurry_migrator@localhost One-time installation and future approved upgrades Can create/alter required tables; remove it after migration unless IT retains it in a password vault.
slurry_ai@AI_SERVICE_IP Future manager-only AI service Read-only access to system_import; create only once approved AI code exists.

There is no operator MySQL account: operators do not receive database credentials. Manager access is the manager PIN in .env, not a MySQL account.

4. Build the final server folder

  1. On the final server, create C:\SlurryManagement under an approved dedicated Windows service account. Do not run the live server from Desktop, OneDrive, a USB drive, or a shared drive.
  2. Recommended: download the reviewed, versioned GitHub Release ZIP and extract its runtime files into that folder. Git is not required on the server; GitHub transfers approved code only.
  3. Do not copy .env, .venv, logs, backups, Caddy private data, or test database files from the test server.
  4. Create a new .env by copying .env.example. Set DB_USER=slurry_web_app and its new password. Set new random SECRET_KEY and MANAGER_PIN.
  5. Run python -m venv .venv, then .venv\Scripts\pip install -r requirements.txt.
  6. Temporarily set DB_USER=slurry_migrator in .env, run .venv\Scripts\python scripts\apply_migrations.py, then immediately restore slurry_web_app credentials in .env.

4A. Approved update workflow

  1. Make and test changes only on the development/test computer.
  2. Commit approved source to GitHub and publish a versioned GitHub Release ZIP.
  3. On the server, back up MySQL before updating.
  4. Extract the approved Release ZIP over runtime application files. Do not overwrite .env, .venv, logs, backups, Caddy private certificate data, or MySQL data.
  5. Run .venv\Scripts\pip install -r requirements.txt only if the release changed requirements.txt.
  6. Run migrations only when the release contains a new numbered migration. Use the temporary migration account, then return .env to the restricted web-app account.
  7. Run Restart_GNEM_Slurry_Tracker.cmd, test the HTTPS link from a second computer, and record the deployed release version.

5. Deploy HTTPS safely

  1. Set the final server IP as reserved/static and configure the name slurry-management.local through internal DNS. Hosts-file entries are acceptable only for a small pilot.
  2. Use WEB_HOST=127.0.0.1, WEB_PORT=5000, and BEHIND_TLS_PROXY=true.
  3. Start GNEM using Start_GNEM_Slurry_Tracker.cmd. It starts the local app and Caddy.
  4. Export the final Caddy root certificate and deploy it through IT/Group Policy, or install it once on each approved factory computer. See 09 HTTPS certificate setup.
  5. Allow inbound TCP 443 only from the factory subnet. Keep 5000 and 3306 inaccessible to employee computers. Do not expose this application to the public internet.

6. Final acceptance test

  • From a second factory computer, open https://slurry-management.local with no certificate warning.
  • Submit one production record and one event; verify both are visible on the server and in system_import.
  • Verify the public display works and shows no manager-only detail.
  • Test manager PIN, then sign out.
  • Connect Power BI using slurry_powerbi; confirm it can read system_import but cannot update data.
  • Run a backup and test restoring it into a non-production database.

7. Clean production release contents

Keep on the server: app, deployment, documentation, migrations, scripts, static_dashboard, main.py, requirements.txt, launcher files, and a local private .env.

Keep in GitHub but not required for runtime: tests, .github, README.md, CHANGELOG.md.

Never commit or copy as a release: .env, .venv, logs, backups, .pytest_cache, Caddy private certificate data, database files, or completed password scripts.
