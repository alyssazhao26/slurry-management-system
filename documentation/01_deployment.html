Complete production deployment and validation

Purpose: This is the authoritative start-to-finish runbook for a new GNEM production installation. Complete it in order and do not begin live entry until every acceptance check passes. Replace every placeholder before running a command.

1. Supported production design

Employee/manager browsers -- HTTPS 443 --> dedicated always-on factory server
                                                |- Caddy HTTPS gateway
                                                |- GNEM on 127.0.0.1:5000
                                                `- MySQL on the server SSD

Power BI computer -------- read-only MySQL 3306 --^ (only its reserved IP)

GNEM, Caddy, MySQL, and the factory server must run for employee entry. Power BI may be off without interrupting GNEM. Do not put production SQL on the Power BI workstation. The current browser does not queue unsaved records while the server is offline.

3. Prepare Windows and the network

  1. Use a dedicated, IT-approved Windows Pro/Server computer with wired Ethernet, SSD, cooling, and UPS. Do not use an employee workstation.
  2. Enable BitLocker, endpoint protection, automatic screen locking, and current security updates.
  3. In BIOS/UEFI enable power restoration after AC loss. In Windows disable sleep and hibernation while plugged in.
  4. Reserve the server and Power BI IPs in DHCP. Create internal DNS for slurry-management.local. A small pilot may instead add SERVER_IP slurry-management.local to each approved device's administrator-controlled hosts file.
  5. Create a standard Windows account such as GNEMService. Give it access only to the application and backup locations; do not use an employee account.
  6. Install supported 64-bit Python 3, MySQL Server 8, MySQL Workbench, and Caddy for Windows. Set the MySQL Windows service Startup type to Automatic.
  7. Confirm the factory network profile is Domain or Private.

4. Copy a clean release

  1. Deploy only a reviewed versioned release that passed python scripts\verify_release.py and the project tests.
  2. Extract it to C:\SlurryManagement. Never run production from Desktop, Downloads, OneDrive, USB, or a network share.
  3. Do not transfer development .env, .venv, logs, database files, backups, test data, or Caddy private data.
  4. Obtain Caddy from its official distribution channel and verify it per IT policy, but keep it in a temporary staging location until after the clean-release check in the next section.

5. Install Python dependencies

Sign in as the service account and run:

cd C:\SlurryManagement
python -m venv .venv
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe scripts\verify_release.py

The verification must pass. Do not bypass a missing/forbidden-file result. After it passes, copy the verified Caddy executable from staging to C:\SlurryManagement\deployment\caddy\caddy.exe. The release checker intentionally rejects bundled executables and private runtime certificate files, so run it on the clean release before adding Caddy.

The two localhost settings are intentional. Restrict .env to Administrators, SYSTEM, and the service account; confirm it is ignored by Git.

8. Apply the database baseline

  1. Temporarily set the migrator username/password in .env.
  2. Run .venv\Scripts\python.exe scripts\apply_migrations.py and require success.

Never edit an applied migration.

9. Permit only Power BI to reach MySQL

Configure MySQL to listen on the reserved server LAN IP in addition to local access; prefer the explicit IP over 0.0.0.0. Restart MySQL and verify GNEM still connects locally. Use MySQL TLS and certificate validation if required by IT. Install the Oracle MySQL connector required by the installed Power BI version.

Power BI is the only supported remote SQL client. Never expose 3306 to the internet, employee/guest networks, or a broad subnet. For Power BI Service refresh, install Microsoft's on-premises data gateway on the approved Power BI/gateway computer.

10. Create narrow firewall rules

In elevated PowerShell, replace both placeholders:

New-NetFirewallRule -DisplayName "GNEM HTTPS - Factory LAN" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 443 -RemoteAddress "FACTORY_SUBNET_CIDR" -Profile Domain,Private
New-NetFirewallRule -DisplayName "GNEM MySQL - Power BI only" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 3306 -RemoteAddress "POWERBI_RESERVED_IP" -Profile Domain,Private

Do not create an inbound rule for 5000. Review pre-existing broad MySQL, Python, Waitress, or Caddy allow rules and remove them only after confirming with IT that another application does not require them. Never port-forward 443, 5000, 3306, RDP, or Caddy administration from the internet.

11. Start HTTPS and distribute its public root

Confirm deployment\caddy\Caddyfile contains:

https://slurry-management.local {
    tls internal
    reverse_proxy 127.0.0.1:5000
}

From the service account run:

cd C:\SlurryManagement
PowerShell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\restart_factory_server.ps1
Get-NetTCPConnection -State Listen -LocalPort 443,5000,3306 | Select-Object LocalAddress,LocalPort,OwningProcess

Port 5000 must bind only to 127.0.0.1; 443 belongs to Caddy; 3306 is local plus the approved server LAN address only if Power BI is enabled.

Caddy normally stores its internal CA under the profile of the account running it at %APPDATA%\Caddy\pki\authorities\local\root.crt. While signed in as the service account, copy only that public file to deployment\caddy\GNEM-Factory-Root-CA.crt. Never copy root.key.

$gnemRoot = [System.Security.Cryptography.X509Certificates.X509Certificate2]::new("C:\SlurryManagement\deployment\caddy\GNEM-Factory-Root-CA.crt")
$gnemRoot | Format-List Subject,Issuer,Thumbprint,NotBefore,NotAfter

Record the thumbprint. Install the public root into Local Computer / Trusted Root Certification Authorities on approved devices, preferably through Group Policy. Restart browsers. Never bypass a certificate warning.

12. Safely delete an existing old GNEM certificate

Only remove a known old GNEM/Caddy root during approved replacement or retirement. Do not bulk-delete by name. Deleting a root breaks trust for everything it signed.

  1. Obtain the old public root file and its approved recorded thumbprint. If neither can reliably identify it, stop and ask IT.
  2. In elevated PowerShell, inspect it:
$oldRoot = [System.Security.Cryptography.X509Certificates.X509Certificate2]::new("C:\ApprovedTemporaryPath\OLD-GNEM-Root.crt")
$oldRoot | Format-List Subject,Issuer,Thumbprint,NotBefore,NotAfter
$oldThumbprint = $oldRoot.Thumbprint
Get-ChildItem Cert:\LocalMachine\Root,Cert:\CurrentUser\Root |
    Where-Object Thumbprint -eq $oldThumbprint |
    Format-List PSParentPath,Subject,Issuer,Thumbprint,NotAfter
  1. Confirm Subject, Issuer, and thumbprint match the deployment record. Keep a restricted recovery copy.
  2. If zero or unexpected multiple certificates appear, stop. Otherwise remove only the exact path(s):
Remove-Item -LiteralPath "Cert:\LocalMachine\Root\EXACT_OLD_THUMBPRINT"
# Only if the verified old root was also found in CurrentUser:
Remove-Item -LiteralPath "Cert:\CurrentUser\Root\EXACT_OLD_THUMBPRINT"
  1. Repeat the lookup to confirm absence. If replacing it, install the new verified root, restart the browser, and test HTTPS.
  2. If Group Policy/device management installed the old root, remove it from that central policy first or it will return.

Never use certutil -delstore Root without an exact thumbprint.

Approved full Caddy CA rotation

Normal renewal needs no deletion. Caddy renews leaf certificates automatically. For an explicitly approved full rotation:

  1. Schedule downtime, verify a current database backup, and plan distribution of the new root.
  2. Stop Caddy. Sign in as the same service account and resolve its actual %APPDATA%\Caddy path.
  3. Copy that entire resolved Caddy directory to a restricted recovery location and verify the copy.
  4. Remove only its verified pki\authorities\local directory and matching certificates\local\slurry-management.local directory. Never delete %APPDATA%, a whole profile, or an unverified computed path.
  5. Restart Caddy, export the new public root.crt, record its thumbprint, distribute it, and validate HTTPS everywhere.
  6. Only then remove the old root from clients using the exact-thumbprint procedure.

Never copy the CA private key to clients or the repository.

13. Install complete automatic startup

MySQL must be an Automatic Windows service. The included installer schedules both GNEM and Caddy. In elevated PowerShell:

cd C:\SlurryManagement
PowerShell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\install_autostart_task.ps1 -TaskUser "GNEM-SERVER\GNEMService"

Enter the password at the Windows prompt. Confirm Task Scheduler shows GNEM Slurry Tracker enabled and, after testing, result 0x0. After validating backup credentials and destination, install maintenance:

PowerShell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\install_maintenance_tasks.ps1 -TaskUser "GNEM-SERVER\GNEMService"

14. Back up and prove restoration

  1. Create C:\GNEM_Backups with access limited to Administrators, SYSTEM, and the service account.
  2. Configure an encrypted off-server copy. A backup on the production SSD alone is insufficient.
  3. Run scripts\backup_factory_database.ps1; require a non-empty timestamped SQL file and no logged error.
  4. Copy it off-server and restore into a separate non-production MySQL instance. Verify both schemas. Never test restore over production.
  5. Record filename, tester, date, result, recovery time, and off-server location.

15. Power BI and permission validation

  1. Connect from the reserved Power BI computer using only slurry_powerbi and import approved system_import tables.
  2. Confirm SELECT succeeds. Confirm INSERT, UPDATE, DELETE, schema changes, and protected slurry_management access are denied using permission inspection or a harmless test object—not destructive statements against real data.
  3. Turn Power BI off temporarily and confirm employee entry continues. Turn it on and verify refresh.

16. Reboot and mandatory acceptance test

Reboot the server. Do not sign in or press a launcher. After startup, test from a second approved computer:

  • [ ] DNS resolves the approved name to the reserved IP.
  • [ ] https://slurry-management.local opens without warning.
  • [ ] 443 is reachable from the factory subnet; 5000 is not remotely reachable.
  • [ ] 3306 is reachable from the reserved Power BI computer only.
  • [ ] MySQL, GNEM, Caddy, startup task, and backup task are healthy.
  • [ ] Operator submits labeled test production and abnormality records and sees them.
  • [ ] Operator can change only permitted open-tracker fields and cannot access manager analysis.
  • [ ] Public display works without exposing manager-only details.
  • [ ] Manager PIN unlocks; sign-out removes access.
  • [ ] Test rows exist in the correct system_import tables.
  • [ ] Power BI reads but cannot write or access protected data.
  • [ ] Backup and off-server copy succeed; non-production restore has passed.
  • [ ] A controlled UPS/power-restoration test powers the server on and restores HTTPS without manual action.

Do not go live with an unresolved check. Remove/exclude test records according to approved data policy.

17. Safe remote maintenance

Use company VPN followed by IT-approved remote administration. Never expose RDP, MySQL, or GNEM publicly.

  1. Test changes away from production and produce a reviewed versioned release.
  2. Record the maintenance window/version and verify a pre-update backup.
  3. Replace runtime files while preserving .env, .venv, logs, backups, Caddy data/private keys, and MySQL data.
  4. Install dependencies only if requirements changed. Apply only new numbered migrations using a temporary migrator.
  5. Run Restart_GNEM_Slurry_Tracker.cmd, then repeat HTTPS, entry, permission, and backup smoke tests.
  6. Record the result and keep the prior release plus verified backup for rollback.

18. Go-live sign-off

Go live only when the restricted deployment record contains all network values, release version, certificate thumbprint, permission-test results, reboot/power-recovery result, verified off-server backup and restore, and approval from the responsible IT and operational owners.

Authoritative GNEM production deployment runbook. Review whenever server, network, database, certificate, startup, backup, or release procedures change.
