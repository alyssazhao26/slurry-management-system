Multi-department deployment and configuration

Decision

Use one shared application codebase and one protected main branch for the common page structure, security controls, reusable display blocks, APIs, migration framework, and release tooling. Each department receives its own environment configuration and database. Department-specific text, fields, calculations, report columns, display choices, and operational records must not be implemented as permanent department branches when they can be represented as configuration or data.

What “shared structure” means

Shared application layerDepartment-owned layer
Navigation, page shells, cards/blocks, dialogs, authentication, audit behavior, API patterns, backup/recovery, and migration runnerBlock titles and content, which blocks are visible, their order and size, field labels/help text/options, event types, report column selections, thresholds, formulas, calculations, and records
Schema capabilities and backward-compatible migration definitionsSeparate database instance/schema populated with that department’s settings and records
Versioned releases and common automated testsDepartment acceptance tests and an approved configuration export/reference

Recommended topology

GitHub main branch + tagged release
             |
             +-- Computer A -- Department A .env -- Department A database
             |                                      `-- A text, fields, formulas, display, records
             |
             `-- Computer B -- Department B .env -- Department B database
                                                    `-- B text, fields, formulas, display, records

Deploy the same reviewed Git tag to both computers. A release can add a new configurable block type or calculation engine without forcing both departments to use identical content or formulas.

Branch policy

  • Keep main as the deployable shared product.
  • Use short-lived branches named for work, such as feature/configurable-calculations or fix/report-column-order, then merge them through review.
  • Do not rename main to a department name and do not create permanent department-a/department-b branches merely for different text, data, fields, calculations, or display settings.
  • A department-specific branch is justified only when that department requires code that cannot safely become a reusable module or configuration capability—for example, a legally required integration exclusive to one site. Record that exception in an architecture decision, assign an owner, and define how shared security fixes will be merged into it.

Configuration model to implement

The current system already stores display blocks, permanent text, field settings, and event choices in the database. Extend the same model rather than adding hard-coded department conditions:

  • Department profile: department code, display name, language, branding text, timezone, and enabled modules.
  • Block configuration: block type, title, content, visibility, order, width, height, and role visibility.
  • Field configuration: stable field key, label, help text, input type, options, required status, validation rule, and report availability.
  • Calculation configuration: stable calculation key, version, input field keys, expression or approved strategy name, rounding/unit rules, effective date, and active status.
  • Report configuration: named templates with selected columns, column order, labels, filters, and department ownership.

Calculation definitions need versioning. Historical records should retain either calculated outputs or the calculation-version identifier so a later formula change does not silently rewrite the meaning of old reports.

Database and migration rules

  • Computer A and Computer B use separate database credentials and databases; never point both departments at one operational schema unless a reviewed multi-tenant design is implemented.
  • Run the same numbered schema migrations on every department database before deploying the matching application tag.
  • Keep secrets and machine-specific values in each computer’s private .env; never commit them.
  • Store editable department configuration in the database. If configuration needs to be promoted or recovered, export it as a sanitized, versioned configuration artifact that contains no operational records or secrets.
  • Back up and restore-test each department database independently.

Release and traceability checklist

  • [ ] Changelog identifies user-visible changes, configuration impact, migrations, and test results.
  • [ ] Architecture documentation is updated when ownership or data flow changes.
  • [ ] Automated tests pass for the shared application.
  • [ ] Department A and Department B acceptance matrices cover their enabled blocks, fields, calculations, and reports.
  • [ ] The exact accepted commit is tagged using Semantic Versioning.
  • [ ] Each deployment record contains department, computer/server, deployed tag, database migration level, configuration version, backup reference, operator, date/time, smoke-test result, and rollback outcome.

Immediate recommendation

Retain the current main name. First make calculations and named report layouts configurable, then deploy the same tagged application to each department with independent databases. This preserves one maintainable product while allowing the contents and behavior of its large blocks to differ by department.
